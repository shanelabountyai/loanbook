# Phase 2 — Amortization + accrual

Goal: the plan (schedule, PRD P0-2) and the truth (daily accrual on the ledger, PRD P0-3), each exact to the cent. Fixtures: `fixtures/amortization/`, `fixtures/accrual/`. Rules: D3 (schedule), D4–D6 (accrual). Do tasks in order; each starts with a failing test. Gate opened 2026-09-30: Shane rebuilt AM1 by hand and it matched to the cent.

- [x] **2.1 Calendar.** Pure date arithmetic on ISO `YYYY-MM-DD` strings, in UTC, with no clock read: `addDays`, `daysBetween`, `addMonthsClamped` (D3: same day-of-month, clamped to month end, always counted from the disbursement date and never chained, so Jan 31 → Feb 28 → Mar 31). Invalid dates are refused. Tests: every due date in AM1–AM5 (AM4 is the clamp case), a leap Feb 29 (2028), `daysBetween` across Feb 29 (AC2's 29 days).
- [x] **2.2 Amortization schedule.** `buildSchedule({ principalCents, aprBps, termMonths, disbursementDate })`, pure, in `src/ledger/`. Installment = one `roundHalfUp` of the exact annuity (bigint numerator and denominator: monthly rate = aprBps / 120000); APR 0 = principal / term, same rounding. Each row's interest = `roundHalfUp(balance × aprBps / 120000)`; principal = payment − interest; the final row pays off the remaining balance (penny problem). Inputs checked at the boundary: `assertCents` and `assertBps`, principal > 0, term a positive integer. Pass AM1–AM5 exactly, every field, including `final_payment_adjustment_cents` and the totals. The schedule is derived on read and never stored. Kill mutants: rounding per step instead of once, final row not absorbing drift, APR 0 path removed.
- [x] **2.3 Loan record + disbursement.** `Loan` table (id, `principalCents`, `aprBps`, `termMonths`, `disbursementDate`) in `prisma/schema/loan.prisma`, append-only by trigger, as the ledger is: terms are facts, and there is no refinancing (non-goal; note the seam). `createLoan(db, terms)` inserts the loan, then posts the disbursement through `postEntry` (Dr loans_receivable / Cr cash, the V1 amounts for L1). No balance column. A loan whose disbursement never posted has zero receivable and accrues nothing. Composing them into one transaction waits for Phase 3, which needs it anyway.
- [ ] **2.4 Accrual math (pure).** Cumulative interest for `d` days in a segment = `roundHalfUp(principalCents × aprBps × d / (10000 × 365))`, denominator 365 in leap years too (D4). Day `d`'s entry = cumulative(d) − cumulative(d−1) (D5). Pass AC1 (986, not 990), AC2 (leap), AC4 (1019 against the schedule's 1000) and AC3's two segments computed separately (329 + 592): every entry and every cumulative value, not just totals.
- [ ] **2.5 Accrual run.** `runAccrual(db, { asOf })` posts every missing day through `asOf` for every loan, one entry per (loan, day): Dr interest_receivable / Cr interest_income. Everything is derived from the ledger, nothing is stored beside it: principal for day D = loans_receivable lines dated before D (D6: a payment on D takes effect D+1, and disbursement day accrues nothing); segment start = the date of the last such line; day number = D − segment start; entry = cumulative(day) − accrual already posted in the segment. **Idempotency is enforced by the database:** a `kind` column on `LedgerEntry` and a partial unique index on (`loanId`, `date`) where `kind = 'accrual'`, so two racing runs leave one entry. `postEntry` takes an optional `kind`. A day whose amount rounds to 0 posts nothing (an entry needs positive lines) and is recomputed harmlessly on the next run. Pass AC5 (a repeat run posts nothing; a skipped day is caught up), AC3 through the ledger (disburse, accrue through 01-25, post a 10000 principal reduction dated 01-25, accrue through 02-14), and AC4's 1019 read back through `trialBalance`. `ledger:verify` is clean after each. Decision line D15 for `kind` and the partial index.
- [ ] **2.6 Accrual command.** `npm run accrue -- --as-of YYYY-MM-DD`: the as-of date is required, and the script never defaults to today (non-negotiable 6). Prints entries posted per loan and exits non-zero on any error. Integration test on a two-loan book over a 31-day run, then `ledger:verify` clean.

**Exit criteria:** AM1–AM5 and AC1–AC5 pass to the cent; accrual is idempotent per (loan, date) at the database layer; no schedule, balance or accrual total stored anywhere; `ledger:verify` clean after a simulated month; CI green, both gates passing.

**Deferred to Phase 3, recorded so they aren't lost:** D9 (the final installment due is the payoff quote, not the schedule's last row); composing several postings in one transaction; paying interest accrued against the schedule's interest (D4: the waterfall allocates against *accrued*).
