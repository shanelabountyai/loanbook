# Phase 3 — Waterfall + payoff

Goal: money in is split by a configured order and every cent of the split is visible (PRD P0-4); a payoff quote for any date is exact, reproducible, and zeroes the loan when paid (PRD P0-6). Fixtures: `fixtures/waterfall/` (WF1–WF10, WFB3/5/10); payoff fixtures do not exist yet (task 3.4 builds them). Rules: D4, D7, D9. Do tasks in order; each starts with a failing test.

- [x] **3.1 Waterfall (pure).** `allocate({ owed: { fees, interest, principal }, paymentCents, order })` in `src/ledger/waterfall.ts`. Each bucket takes min(remaining payment, owed), in `order`; the order is an argument, never a constant inside the function (PRD P0-4: config, not code). Refused up front: `non_positive_payment` (WF9), `exceeds_payoff` carrying `payoff_cents` (WF8), a non-integer amount, an order that is not a permutation of the three buckets. Pass WF1–WF10 and WFB3/5/10: allocation, remaining, `loan_closed`. No rounding anywhere (it is subtraction); a lint-clean file proves it. Mutants to kill: order hard-coded, `min` replaced by always-full, `>` for `>=` at exact payoff (WF7).
- [x] **3.2 Owed from the ledger.** `owedCents(db, loanId)` reads fees / interest / principal for one loan from `trialBalance`'s per-loan view (balance = sum of lines, nothing stored). This is what D4 means by "allocate against *accrued*": interest owed is `interest_receivable`, not the schedule's interest. Test: L1 after disbursement + the AC4 accrual reads 100000 / 1019 / 0.
- [x] **3.3 Payment posting.** `postPayment(db, { loanId, date, paymentCents, order })`: reads owed, allocates, posts **one** entry per payment, Dr cash / Cr one line per bucket touched (a zero bucket gets no line, WF6), `loanId` on the entry. Needs the transaction-composition work Phase 2 deferred: the read and the post must be one transaction, so two racing payments cannot both be allowed against the same owed amount (the second sees the first's lines or is refused). `postEntry` currently owns its transaction (NEXT.md); decide here whether to give it an optional caller-owned transaction or lock the loan row, and record it as D16. Pass WF1–WF7 and WFB3/5/10 through the real posting path and compare journal lines as an unordered set plus the cash line (fixtures README). A payment dated D applies after D's accrual (D6): accrual for D must already be posted or the payment on D is refused (`accrual_pending`) rather than allocating against stale interest; record in D16. `ledger:verify` clean after each.
- [x] **3.4 Payoff quote.** Gate first: extend `tools/build_fixtures.py` and `tools/verify_fixtures.py` with payoff fixtures PO1–PO4 (quote on an accrual day; quote mid-segment after a principal reduction; quote with a fee outstanding; quote on the disbursement day), regenerate, `verify_fixtures.py` prints OK, review the diff. Then `payoffQuote(db, { loanId, asOf })` = principal + interest accrued through `asOf` (by the same cumulative rule as D5/D15, **without posting**) + unpaid fees. Pure read, deterministic: same inputs, same output (PRD P0-6). The quote is logged with its inputs. Decision line D17 for the quote's date convention (a quote for D includes D's accrual, so a payment on D at the quote closes the loan).
- [x] **3.5 Payoff round-trip.** Quote for D, accrue through D, pay the quote on D through `postPayment`: all three sub-accounts are exactly zero, `loan_closed`, `ledger:verify` clean (PRD P0-6 round-trip). Overpayment by 1 cent is `exceeds_payoff` (WF8 through the real path). D9: a loan paid on its schedule to the final due date owes exactly the quote on that date, not the schedule's last row; test it on L1 so the schedule's drift (D4) lands in the final payment and the loan closes to zero.
- [ ] **3.6 Payment command + late-fee config.** `npm run pay -- --loan <id> --date YYYY-MM-DD --cents N` (all required, never defaults to today); prints the split; exits non-zero on any refusal. The late fee amount (open item 2, flat 1500¢ in the fixtures) lives in one config constant and is only *read* by Phase 4's assessment; this task only adds the constant and a test that the waterfall order and fee amount come from config, not literals. Integration test: a two-loan book, one short payment, one exact, one payoff; `ledger:verify` clean.

**Exit criteria:** WF1–WF10 and WFB3/5/10 pass through the real posting path to the cent; payoff round-trip zeroes every sub-account; D9 holds on L1; two racing payments cannot over-collect; no stored balance, split or quote; `ledger:verify` clean after each scenario; CI green, both gates passing.

**Deferred to Phase 4:** assessing late fees (the delinquency job posts Dr fees_receivable / Cr fees_income at grace exit), delinquency from partial payments (open item 3), write-off treatment, views.
